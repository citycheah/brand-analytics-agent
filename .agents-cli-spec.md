Agent Spec: Brand Social Media & SQL Analytics Agent 

  This is the official specification for the Brand Social Media & SQL Analytics Agent.
  ──────
  The Brand Social Media & SQL Analytics Agent is an automated multi-agent system designed to assist marketing researchers and brand analysts. It performs five primary operations:

  1. Official Brand Identity Discovery: Searches the web to find official social media handles (Twitter/X, Instagram, Facebook, LinkedIn, TikTok, YouTube, etc.), official website domains (both local market
  and global, e.g.  bmw.de ,  mercedes-benz.com ), and well-known brand aliases (e.g.,  Mercedes ,  BMW Group ) for a user-provided list of brands.
  2. Secure Database Querying: Uses the discovered brand identities (handles, domains, and aliases) to query a BigQuery table safely. It filters records by user-specified date range and target country/market,
  performing a regular expression search across multiple text fields based on a provided SQL template.
  3. Structured Metrics Calculation: Calculates Share of Voice (SOV / Share of Impressions) and Share of Spend (SOS) for each brand in the list using predefined Python metrics tools (pandas) inside the
  isolated container, presenting a structured summary table and report.
  4. Export & Custom Insights: Exports raw data as CSV and the final structured report as HTML/Markdown. Provides context-aware follow-up questions to the user in the chat interface, and executes on-the-fly Python scripts within a secure, sandboxed Code Interpreter to answer custom user questions.
  5. Brand Feasibility Checking: Evaluates whether each brand's impressions (default > 300,000 per quarter) or spend (default > 7,500 per quarter) meets business feasibility thresholds. Allows the user to customize these thresholds via chat, and supports scaling them for different date ranges and future country-specific overrides.

  To prevent conversational state loops, reset loops, and query interruptions, the system is designed as a Single Persistent Conversational Agent:
  •  DataAnalystAgent  (A single durable conversational analyst agent that owns the user conversation, manages parameters collection, and executes all necessary tools—including wrapping the BrandIdentityFinderAgent as an AgentTool.)

  ## 2. Example Use Cases

  ### Scenario: Compare automotive brands in Germany for Q1 2026
  #### User Input:
  • Brands:  ["BMW", "Mercedes-Benz"] 
  • Target Country:  Germany 
  • Date Range:  2026-01-01  to  2026-03-31 
  #### Agent Execution Sequence:
  1. Phase 1: Brand Identity Discovery
      • Agent searches the web for Mercedes-Benz and BMW official social media handles, website domains, and well-known aliases (focusing on both global and German-specific entities).
      • Discovered BMW Identity:
          • Handles:  ["bmw", "bmw_de"] 
          • Domains:  ["bmw.com", "bmw.de"] 
          • Aliases:  ["bmw group", "bayerische motoren werke"] 
      • Discovered Mercedes-Benz Identity:
          • Handles:  ["mercedesbenz", "mercedesbenz_de"] 
          • Domains:  ["mercedes-benz.com", "mercedes-benz.de"] 
          • Aliases:  ["mercedes", "mercedes-benz group"] 

  2. Phase 2: Database Query & Confirmation
      • The Brand Analytics AI Agent (DataAnalystAgent) gathers missing target inputs from the user (country="Germany", start_date="2026-01-01", end_date="2026-03-31") and prompts for confirmation to proceed.
      • The Brand Analytics AI Agent invokes the BrandIdentityFinderAgent tool to discover official identifiers.
      • The Brand Analytics AI Agent formats the SQL script using the table:  your-gcp-project.brand_analytics.competitive_ad_occurrences  (whitelisted from  .env ).
      • Replaces  include_keywords  with all discovered identifiers.
      • The Brand Analytics AI Agent executes the query via execute_bq_query, reporting only the count of records found. It does NOT automatically calculate totals or display a summary table.
      • The Brand Analytics AI Agent explicitly asks the user to confirm/select which analysis format they want to run.
  3. Phase 3: Interactive Analysis Selection
      • The user requests "Calculate Share of Spend and Share of Voice".
      • The DataAnalystAgent processes the raw rows through calculate_brand_metrics to compute SOV and SOS percentages.
      • The DataAnalystAgent calls export_report and prints the complete detailed Markdown table.

  ## 3. Tools Required

  ### A. Web Search Grounding Tool (Finder Agent only)

  • Tool:  google_search  (Built-in ADK grounding)
  • Purpose: Find official social links, handle strings, website domains, and well-known brand aliases.

  ### B. Brand Identity Finder Tool (DataAnalystAgent only)

  • Tool:  BrandIdentityFinderAgent  (AgentTool wrapping FinderAgent)
  • Purpose: Discovers handles, official domains, and aliases by calling the web search grounding tool for each brand, returning them to the analyst agent.

   ### C. BigQuery Query Tool (DataAnalystAgent only)
 
   • Tool:  execute_bq_query(start_date: str, end_date: str, target_countries: list[str], include_keywords: list[str], exclude_keywords: list[str]) 
   • Purpose: Replaces placeholders in  query_template.sql  and queries the BigQuery table specified by the  .env  variable  BQ_TABLE_NAME .
   • Extraction: Runs a BigQuery Extract job to dump the query results to a country and date-range partitioned subfolder under the GCS session folder (gs://{bucket_name}/tmp_bq_extracts/session_{session_id}/country={country}/date_range={start_date}_{end_date}/). Purges any matching pre-existing partition files prior to running the query to prevent duplicates.
   • Return Format: Returns a metadata dictionary containing the `"status": "success"` key, the `gcs_uri` session root, the dataset schema, row count, and a small subset of preview rows instead of loading the raw dataset directly into the chat history. Supports querying multiple countries simultaneously.
   • API Dependencies:  google-cloud-bigquery  Python SDK.
   • Authentication: Service Account with  BigQuery Data Viewer  role.
 
   ### D. Predefined Metrics Calculation Tool (DataAnalystAgent only)
 
   • Tool:  calculate_brand_metrics(bq_data: dict | list[dict], brand_keywords_map: dict) 
   • Purpose: Securely calculates SOS and SOV metrics using Python ( pandas ), loading raw data recursively from all partition folders under the GCS session root directory. Resolves and appends country and date-range path metadata as DataFrame columns. Deduplicates all loaded rows using only hashable columns to prevent double-counting when query dates overlap. Maps returned keywords/domains/aliases back to their respective brands.
   • Return Format: Returns a dictionary containing the calculated SOS and SOV metrics grouped by country, along with the `"status": "success"` key.
   • API Dependencies:  pandas ,  pyarrow ,  gcsfs .
 
   ### E. Predefined Report Metrics Calculation Tool (DataAnalystAgent only)
 
   • Tool:  calculate_report_metrics(bq_data: dict | list[dict], brand_keywords_map: dict, report_type: str) 
   • Purpose: Computes dashboard-specific report metrics based on the chosen format (e.g. `trends_sos_sov`, `channel_group`, `publisher`, `feasibility`, `comprehensive`, `dynamic`). Resolves raw records from GCS, builds interactive Plotly chart structures dynamically, and stores them in a local/GCS cache.
   • Return Format: Returns a dictionary containing `"status": "success"`, the `"report_cache_id"`, and calculated metadata summary.
   • API Dependencies:  pandas ,  plotly .
 
   ### F. Brand Feasibility Checking Tool (DataAnalystAgent only)
 
   • Tool:  check_brand_feasibility(bq_data: dict | list[dict], brand_keywords_map: dict, spend_threshold: float, impressions_threshold: int, start_date: str, end_date: str, creative_verifications: dict | list[dict], target_category: str) 
   • Purpose: Evaluates whether each brand's aggregated spend or impressions meet the business feasibility thresholds. Resolves raw records from GCS, scales thresholds proportionally to the query duration computed in Python using `start_date` and `end_date`, filters out ads that fail creative verification or do not match `target_category`, and checks feasibility.
   • Return Format: Returns a dictionary mapping each country and brand to its feasibility details, along with the `"status": "success"` key. Accepts either a raw list or a dictionary wrapper containing the `verifications` key for creative verifications.
 
   ### G. Code Interpreter Tool (DataAnalystAgent only)
 
   • Tool:  sandboxed_python_interpreter(script: str, data_uri: str = None) 
   • Purpose: Securely execute dynamically generated Python scripts to provide custom insights and answer user follow-up questions on the fly. The sandbox environment automatically pre-loads a pandas DataFrame named `df` from `data_uri` (GCS or local path) so that custom scripts can run immediately without executing storage downloads or needing credentials.
   • Return Format: Returns a dictionary with `"status": "success"` and an `"output"` key containing stdout on successful execution, or `"status": "error"` and an `"error"` key on validation/runtime failures (replacing the previous boolean success flags).
   • Constraint: Must run in an isolated sandbox with no network/write access to the host environment.
 
   ### H. Export Tool (DataAnalystAgent only)
 
   • Tool:  export_report(country: str, start_date: str, end_date: str, report_cache_id: str, feasibility_data: dict, creative_verifications: list[dict], user_request_context: str) 
   • Purpose: Dynamic, LLM-backed report export tool. Runs a sub-agent to generate a custom, beautifully styled HTML analytics report from the session analysis results, rendering interactive Plotly charts injected from the report cache. Saves output report using the ADK Artifact Service, returning the downloadable HTTPS Cloud Storage console URI (or localized file URI fallback). Writing to local disk is a development-only convenience guarded by the `LOCAL_DEV_WRITE` environment flag. CSV raw data export is excluded.
   • Return Format: Returns a dictionary containing `"status": "success"`, the `"html_filename"`, `"html_file_uri"`, and a `"summary"` string.
 
   ### I. Multimodal Creative Verification Tool (DataAnalystAgent only)
 
   • Tool:  verify_creatives_multimodal(bq_data: dict | list[dict], brand_keywords_map: dict, brand_domains_map: dict, target_category: str, spend_threshold: float, impressions_threshold: int, start_date: str, end_date: str) 
   • Purpose: Evaluates creative ad alignment for multiple brands concurrently by loading the full dataset directly, grouping and sorting by impressions, and executing model verifications. Uses domain-level pre-filtering (auto-approving creatives if their domains match the brand's official website domains) and early stopping (skipping evaluation if a brand's verified metrics already meet the active spend or impressions thresholds). Runs chunked batch verification via Gemini model to check alignment, categorise the featured product dynamically, and return verified compliance results. Bypasses standard Gemini API video limitations by separating and processing video files (.mp4) individually (batch size of 1) while processing images/other assets in chunked batches (batch size of 5).
   • Return Format: Returns a dictionary structured with `"status": "success"` and a `"verifications"` list key containing all creative verification records. Parameter batching and concurrency configs are managed internally via environment variables. Deduplicates results by `(url, country)` tuples.
   • API Dependencies:  google-genai .

  ## 4. Constraints & Safety Rules

  1. Strict Table Enforce (Read-Only Whitelist & Validation):
      • The BigQuery tool MUST read the table name only from the environment variable  BQ_TABLE_NAME .
      • The tool MUST validate that  BQ_TABLE_NAME  strictly matches the regex pattern  ^[a-z0-9_.-]+$  before performing string interpolation. Any deviation must instantly abort the query.
      • The tool MUST block any SQL queries containing write/mutation keywords (e.g.,  INSERT ,  UPDATE ,  DELETE ,  DROP ,  ALTER ,  MERGE ).
      • The query MUST only be a single  SELECT  statement.
  2. Country/Market Whitelist Validation:
      • The agent and tools MUST enforce a strict whitelist validation check against the 49 supported countries/markets loaded from the environment variable `SUPPORTED_COUNTRIES`.
      • Semicolon (`;`) delimiter MUST be used in the `.env` variable to safely parse country names that contain commas (such as `"Taiwan, Province of China"` and `"Korea, Republic of"`).
      • Under the parameter gathering phase (Phase 1), if the user inputs an unsupported country, the `DataAnalystAgent` MUST halt, advise the user that the market is not supported, and prompt them to select a valid country.
      • The `execute_bq_query` tool MUST validate that all values in `target_countries` are whitelisted (case-insensitive) and throw a `ValueError` to block querying for unsupported markets.
  3. Sandboxed Code Execution Only:
      • Unsandboxed dynamic code execution ( eval  or  exec  in the main agent process) is STRICTLY PROHIBITED.
      • Standard metrics and aggregations MUST be handled by the predefined  calculate_brand_metrics  tool.
      • Feasibility evaluations MUST be handled by the predefined  check_brand_feasibility  tool.
      • On-the-fly custom data analysis MUST ONLY be executed within the secure, isolated  sandboxed_python_interpreter  tool.
  4. Conversational Analyst Agent Orchestration & Interactive Prompts:
      • The `DataAnalystAgent` is the central interface responsible for gathering required parameters (Brands, Date Range, Country) interactively from the user and requesting confirmation.
      • **User-in-the-Loop Typo Detection**: The `DataAnalystAgent` MUST evaluate requested brand names for obvious typos upfront. If a typo is suspected (e.g., "Marcedes"), it MUST halt and ask the user to confirm the correct spelling before calling any tool or querying the database.
      • The `DataAnalystAgent` must strictly delegate brand identification to the `BrandIdentityFinderAgent` tool and must not attempt to guess identifiers.
      • The `DataAnalystAgent` must execute the query first and report the number of records found. If the user has already requested a specific analysis (e.g. SOS/SOV or feasibility) in their prompt or history, it must proceed directly to run it. Otherwise, it must explicitly ask the user what specific analysis they want to run (e.g., SOS/SOV, Feasibility Checks, Custom Python Script) rather than assuming a default action.
      • **Interactive Report Type Selection**: If the user requests to export reports or save the data, the agent MUST stop and ask the user which report type they want to export (e.g. SOS/SOV, Channel Group, Publisher, Feasibility, Comprehensive, Dynamic). Once chosen, the agent calls `calculate_report_metrics` and `export_report` with the chosen cache ID.
      • **Multi-Country Loop Export**: If multiple countries were analyzed in the session, the agent MUST call `export_report` separately in a loop for each country, rather than bundling them together.
  5. Code Preservation:
      • Any future upgrades or refactorings of files must isolate changes to target modules, keeping surrounding configurations intact.
  6. Keyword Quality & Uniqueness (Brand Identity Discovery):
      • **Iterative Search Reasoning Loop & Split Queries**: The `BrandIdentityFinderAgent` MUST run an iterative reasoning loop. If the initial query misses links for key platforms (Twitter/X, Instagram, Facebook, LinkedIn, TikTok, YouTube), it MUST execute platform-specific queries (e.g. `<BrandName> official TikTok account <Country>`) to recover the missing handles.
      • **Low Randomness Configuration**: Both the `BrandIdentityFinderAgent` and its underlying search sub-agent MUST be configured with a model temperature of `0.1` to ensure stable, deterministic search query routing and handle extraction.
      • **URL-Based Handle Extraction**: The `BrandIdentityFinderAgent` MUST analyze the URLs returned in search results to parse official handles directly (e.g. extracting `bmw_de` from `instagram.com/bmw_de`).
      • **Brand Name Keyword Enforce**: The lowercased brand name itself MUST always be included in the aliases/keywords list mapped by the agent, ensuring full exact-match query coverage.
      • No Keyword Overlap Between Brands: Each keyword (handle, domain, alias) MUST be unique to exactly one brand. If a keyword could match multiple brands, it MUST be qualified with the brand name (e.g., use  haribo gummibärchen  instead of bare  gummibärchen ).
      • Precision Over Recall: Generic dictionary words (e.g.,  kinder  meaning "children",  drachen  meaning "dragons",  orange  matching color/fruit/telco) MUST NOT be used as standalone keywords. All such words MUST be combined with the brand name or product qualifier.
      • Plain Text Only: All keywords MUST be provided as lowercase plain-text strings, NOT regular expressions. The agent must NOT add  \b  boundaries or escape characters; the SQL template natively handles auto-escaping and boundary matching for exact precision.
      • The  brand_keywords_map  dict passed to  calculate_brand_metrics  and  check_brand_feasibility  MUST exactly mirror these plain-text strings to ensure proper row attribution downstream.
      • The `BrandIdentityFinderAgent` tool MUST verify the final keyword list against these rules before returning them to the `DataAnalystAgent`.
  7. Context-Aware Follow-ups:
      • At the end of every final analysis response, the agent MUST present 1-3 context-aware follow-up questions interactively in the chat interface to suggest what the user might want to analyze next.
  8. Customizable Brand Feasibility Checking & On-Demand Threshold Prompts:
      • The agent MUST NOT ask the user regarding the feasibility thresholds until the user explicitly requests a feasibility check.
      • When the user asks for a feasibility check, the agent MUST present the default thresholds scaled at the ceiling month level (where months = max(1, math.ceil(days / 30.0)) relative to a 3-month/quarter base, using start_date and end_date), and ask the user if they want to customize them.
      • The agent MUST also ask the user whether to run creative verification. If the user decides it is not needed, `verify_creatives_multimodal` is bypassed.
      • Once confirmed, these values are passed to `check_brand_feasibility` along with the start_date, end_date, country, and any verification results.
      • The threshold logic must remain open and flexible to allow country-specific default threshold rules to be resolved.
  9. Multimodal AI Creative Verification & Post-Filtering:
      • If the user confirms they want creative verification, the agent MUST pass the raw query data handle `bq_data`, `brand_keywords_map`, `brand_domains_map`, unscaled `spend_threshold` / `impressions_threshold`, and `start_date` / `end_date` to `verify_creatives_multimodal`.
      • **Brand-First Grouping & Ordering**: Creatives MUST be grouped by brand first, and then grouped by creative URL (summing metrics) and sorted descending by impressions.
      • **Sequential Early-Stopping**: Verification runs brand-by-brand sequentially. Once a brand's spend/impressions hit the scaled thresholds, verification for the remaining creatives of that brand stops immediately.
      • **Always-on Domain Pre-filtering**: Enabled only when `target_category` is not specified. If `target_category` is provided, domain pre-filtering is bypassed so Gemini can classify the category.
      • **Caching & De-duplication**: Gemini verification results are cached globally by URL to avoid duplicate calls. Unique creatives are output exactly once in the final result list.
      • **Enforced Presentation Table Format**: Results MUST be presented in a markdown table. CRITICAL: If multiple countries were analyzed, a separate markdown table MUST be rendered for each country (labeled `### Creative Verification - [Country]`). The columns MUST be: `Creative` (clickable link `[short_name](URL)`), `Brand`, `Category`, `Product`, `Spend (USD)`, `Impressions`, and `Status` ("Belongs to brand" / "Does not belong to brand"). DO NOT show Gemini's reasoning/explanation.
      • **Feasibility Integration & Threshold Scaling**: Both `check_brand_feasibility` and `verify_creatives_multimodal` scale thresholds internally based on query dates. The agent MUST pass unscaled base thresholds to prevent double-scaling. `check_brand_feasibility` MUST exclude any unverified or skipped creative rows when creative verification is selected. The conversational analyst model and the report model MUST determine the final Feasibility Status strictly using the "is_feasible" boolean key returned by the check_brand_feasibility tool instead of trying to compute or verify the rules themselves.
  10. Secure Telemetry and Session Correlation Logging Callbacks:
      • To enable centralized debugging, auditing, and performance tracing, the multi-agent application registers security-hardened lifecycle callbacks (`before_model_log`, `after_model_log`, `before_tool_log`, `after_tool_log`) on all agents.
      • **Session ID Correlation**: Every log statement generated within these callbacks dynamically extracts the unique session identifier (`callback_context.session.id` or `tool_context.session.id`) and prefixes the log record with `[Session: <session_id>]` to facilitate log-stream filtering in Cloud Logging.
      • **Privacy Protections**: Callbacks must never log conversational text content (such as raw user queries or model text responses), preventing leakage of client credentials, Google Cloud Storage links, or private snapshots. Logs should only capture token sizes, model names, safety blocks, triggered tool names, and metadata.
      • **Keyword Alignments**: Tool logger signatures must strictly match the ADK keyword calling patterns: `before_tool_log(tool, args, tool_context)` and `after_tool_log(tool, args, tool_context, tool_response)`.

  ## 5. Success Criteria

  1. Accuracy of Brand Identity Discovery:
      • Discovered handles, official domains, and aliases must match the official brand names and localized variations (verified against manual tests).
  2. Correctness of SQL Queries:
      • Auto-generated BigQuery queries must execute without syntax errors and strictly respect the user's date range and country filters.
  3. Calculation Integrity:
      • Computed SOV and SOS metrics must sum up to exactly 100.00% across the user's provided list of brands.
  4. Validation Pipeline:
      • Evaluation dataset passes  agents-cli eval run  with a response-correctness threshold of >90%.
  5. Multimodal Verification Accuracy:
      • Gemini multimodal verification must correctly classify creative brand alignment and extract product categories, matching our manual test assertions for audited ads.

  ## 6. Development Method (Strictly Test/Eval-First)

  To guarantee software quality and prompt safety, we strictly adhere to a Test-Driven & Eval-Driven Development (TDD/EDD) process:

  1. Mock Data Creation: Generate offline BQ mock response datasets first inside  tests/mocks/ .
  2. Unit & Integration Test Suites: Implement unit tests (e.g.,  tests/unit/test_metrics.py  for SOS/SOV formulas) prior to implementing the core calculation tools.
  3. Eval Dataset Synthesis: Author complete ADK evaluation schemas ( tests/eval/datasets/brand_analytics_cases.json ) before generating prompt logic.
  4. Iterative Coding: Generate code and agent prompt configurations after the entire validation harness is fully in place.
